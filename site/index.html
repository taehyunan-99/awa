Agents Watching Agents

에이전트가 에이전트를 감시한다

AWA는 오케스트레이션 도구가 아니라 감독된 자율성(Supervised Autonomy) 플랫폼입니다.
자율은 에이전트에게, 검증·권한·안전은 시스템에게.

왜 — 에이전트에게 큰 작업을 맡기면 생기는 일

AI 에이전트 하나에게 큰 작업을 맡기면 세 가지가 반복됩니다. AWA는 각각에 구조적인 답을 둡니다.

🟥 False green
스스로의 맹점
에이전트가 쓴 테스트는 에이전트가 쓴 코드의 맹점을 공유합니다. → 독립 리뷰어 3종이 투표, 만장일치 차단이면 자동 수정.
🟧 권한 폭주
병목 vs 사고
매번 물으면 사람이 병목(실측 58회), 전부 허용하면 rm -rf 한 번에 끝. → 승인 패턴은 학습, 위험 명령은 우회 불가.
🟨 컨텍스트 절단
흐름이 끊긴다
auto-compact가 task 중간에 끼어들어 흐름을 끊습니다. → task 경계마다 선제 정리, 흐름은 파일에 저장.
📊
비용은 단일 에이전트와 동급.
동일 plan을 단일 에이전트 1회 + AWA 3회(n=3) 실측 — 사람 개입 58회 → 2회(28배↓), 토큰 사용량은 비슷, 그러면서 false-green 2건을 실제로 차단했습니다.
7명인데 토큰이 동급인 이유: 리뷰어는 전체 맥락이 아니라 diff와 results/만 읽고, 게이트가 재작업을 줄여 그만큼 상쇄됩니다.
STEP 1 설치

설치

AWA는 Claude Code 스킬로 설치됩니다. 먼저 네 가지 의존성이 필요합니다 — 하나라도 없으면 런타임에 조용히 실패하므로 먼저 확인하세요.

필수 의존성
tmux jq claude uuidgen
tmux는 멀티 에이전트 페인, jq는 신호 파싱, claude는 워커 프로세스,
uuidgen은 세션 ID에 쓰입니다.
설치 방식
install.sh가 의존성을 검사한 뒤 ~/.claude/skills/awa로 복사
설치합니다. 영역 가이드(AGENTS.md 등)는 제외됩니다.
terminal — bash
# 의존성: tmux · jq · claude (Claude Code CLI) · uuidgen
$ git clone https://github.com/taehyunan-99/awa.git
$ cd awa/.claude/skills/awa
$ bash install.sh
 
✓ 의존성 확인 — tmux, jq, claude, uuidgen
✓ 설치 완료 → ~/.claude/skills/awa
⚠️
의존성이 하나라도 빠지면 install.sh가 설치 전에 멈춥니다. macOS는 brew install tmux jq, Claude Code CLI는 공식 문서를 참고하세요.
📍
설치하고 나면 clone 폴더는 지워도 됩니다. AWA는 ~/.claude/skills/awa로 복사되므로,
이후로는 작업하려는 아무 프로젝트 폴더에서 claude를 열고 /awa만 치면 됩니다 — clone 위치와 무관합니다.
STEP 2 시작하기

/awa 첫 실행

작업할 프로젝트 폴더에서 Claude Code를 띄우고 /awa를 입력하면, 인터뷰가 시작됩니다.
AWA는 항상 현재 폴더가 아니라 사용자가 고른 프로젝트 폴더에서 동작하므로, 어디서 실행하든 안전합니다.

🧭
/awa 슬래시 명령 하나면 충분합니다. 인터뷰가 내부적으로 awa-up.sh를 호출해 팀을 띄웁니다
harness/bin/*.sh를 직접 칠 일은 자동화·고급 용도뿐입니다. 인터뷰가 출력하는 명령을 실행할 땐 Claude Code 입력창에서 !를 앞에 붙여(예: !awa-up.sh …) 그 자리에서 셸로 실행합니다.
이 가이드에서 $는 일반 터미널, >는 Claude Code 입력창을 뜻합니다.
myapp — claude
$ cd ~/projects/myapp
$ claude
 
> /awa
인터뷰가 작업을 보고 필요한 역할만 조립합니다…
💡
팀은 고정 프리셋이 아닙니다. /awa 인터뷰가 작업을 분석해 필요한 역할만 조립하고 📄 .awa/team.yaml로 저장합니다.
다음에 같은 폴더에서 /awa를 다시 실행하면 이 구성을 그대로 이어서 띄울 수 있습니다.
STEP 3 팀 조립

팀 조립 인터뷰

인터뷰는 채팅으로 진행됩니다. 프로젝트 폴더를 정하고, plan을 검토하고, 작업에 맞는 팀을 조립한 뒤 띄울 명령을 출력합니다.
모든 단계는 사용자 확인을 거칩니다.

프로젝트 폴더 선택

워커들이 읽고 수정할 폴더를 고릅니다. 현재 터미널 폴더를 후보로 제시하거나, 경로를 직접 입력하거나, 저장된 북마크에서 고를 수 있습니다.
git 저장소가 아니면 git init을, .awa/ 추적 여부를 확인합니다.

plan 검토 (4축 리뷰) · 난이도 게이트

docs/plan.md → docs/plans/ → docs/superpowers/plans/ 순으로 plan을 자동 탐색합니다.
plan을 찾으면 완결성·실행가능성·기술건전성·검증가능성 4축으로 리뷰하고, 결함이 있으면 수정안을 제안합니다.

plan이 없으면 자연어로 작업을 설명할 수 있습니다. 단, 다도메인·상태 전이·불변식이 많은 복잡한 작업이면 난이도 게이트가 plan 작성을 먼저 권유합니다.
plan 없는 큰 작업은 감시의 닻(plan-anchored)이 약해지기 때문입니다. "그래도 자연어로 진행"을 고르면 계속할 수 있습니다.

역할 자율 조립

AWA가 작업을 분석해 역할 카탈로그에서 필요한 역할만 골라 팀을 조립하고 근거를 설명합니다. 정적 템플릿을 통째로 던지지 않습니다.
예: "메모 웹앱이라 frontend·backend·infra 3명, plan 정합·품질 리뷰어를 붙였습니다. 인증/DB 불필요라 security 워커는 뺐습니다."

가감 · 리뷰 수위 · 저장

역할을 더하거나 빼고, 리뷰 수위를 정한 뒤 📄 .awa/team.yaml에 저장합니다.

모드 선택 (단일 / 멀티뷰)

마지막으로 모드를 고르면 띄울 명령이 출력됩니다. 이미 떠 있는 AWA 팀이 없으면 단일(single)로 자동 진행하고, 하나라도 있으면 단일과 멀티뷰 중 고릅니다.
멀티뷰는 여러 프로젝트를 한 관제탑(_DASHBOARD)에 모아 동시에 감시하는 모드입니다(자세히는 운영·관리 › 멀티뷰 관제탑).

역할 카탈로그

조립의 원자 단위입니다. 권한은 역할에서 자동으로 파생됩니다.
워커는 작업 경로만 쓰기 가능하고, 리뷰어·review-mgr은 읽기 전용입니다.
ORCH가 작업을 보고 이 카탈로그에서 필요한 역할만 골라 조립합니다.

🏷️
역할명과 화면 속 이름은 같은 것입니다. 같은 역할이 여럿이면 backend-1·backend-2처럼 번호가 붙고, 리뷰어는 화면에서 alignment-rev·quality-rev·security-rev로 줄여 표시됩니다 — 아래 reviewer-alignment 등과 동일물입니다.
워커 작업 경로 쓰기 가능
engineer
범용 구현 워커. 도메인을 가리지 않습니다.
셸 스크립트·설정 파일·빌드 글루·자동화 등 frontend/backend/infra로 딱 떨어지지 않는 일을 맡습니다.
작업이 단순하거나 한 명이면 충분할 때 기본 선택.
frontend
UI·클라이언트 구현 전담. 컴포넌트·상태·스타일·접근성 등 화면 쪽 작업. 풀스택 작업에서 backend·infra와 분업합니다.
backend
서버·API·도메인 로직·데이터 계층 구현. "API만 만들면 되는" 작업이면 frontend 없이 backend 한 명만 조립되기도 합니다.
infra
배포·CI·컨테이너·환경 설정 등 인프라 작업. 코드와 운영 사이를 잇습니다.
tester
테스트 작성 전담 워커. 구현 워커와 분리돼 있어, 구현자가 자기 코드에 맞춰 테스트를 쓰는 false-green을 구조적으로 줄입니다.
security
보안 점검·코드 감사 워커. 실제로 수정·강화 작업을 합니다. (게이트에서 투표하는 security 리뷰어와는 별개 역할.)
researcher
조사·비교 전담 — 읽기 전용. 코드를 바꾸지 않고 코드베이스 탐색·기술 비교·근거 수집만 합니다.
투표 리뷰어 읽기 전용 · 합의 게이트의 표
reviewer-alignment
결과물이 plan의 의도·기준에서 벗어나지 않았는지 검토. "요구한 것과 다른 걸 잘 만든" 드리프트를 잡는 표.
reviewer-quality
구현의 견고함과 테스트의 실효성을 검토. 통과하는 테스트가 실제로 무엇을 보장하는지까지 봅니다.
reviewer-security
취약점·권한 누수·계약 위반을 검토하는 표. 각 리뷰어는 독립 컨텍스트에서 판단해 한 명의 단독 거부권이 아니라 합의를 만듭니다.
관리 읽기 전용 · 투표권 없음
review-mgr
리뷰어들의 표를 집계하고 작업의 드리프트를 시계열로 추적하는 관리자. 직접 투표하지는 않습니다.
투표 리뷰어가 2명 이상이면 자동으로 따라붙습니다.
🗳️
투표 리뷰어는 0명 또는 2명+ 만 됩니다. 1명은 합의가 아니라 단독 거부권이라 불변식 위반으로 거부됩니다.
리뷰를 가볍게 하려면 무리뷰(0명), 둘 거면 최소 2종(예: alignment+quality)을 붙이세요. 2명+면 review-mgr가 자동으로 따라옵니다.

작동 원리 감시 회로

감시 4축

워커의 "끝났다"는 그대로 믿지 않습니다. 모든 신호는 파일 IPC로 흐르며(화면 파싱 없음), 감시는 네 축으로 상시 작동합니다. 이것이 AWA의 정체성입니다.

plan-anchored
plan은 읽고 버리는 문서가 아니라 전 구간의 닻 — task마다 기준 명시·검증
drift-tracked
의도에서 벗어나는 순간을 시계열로 상시 추적
permission-gated
권한은 매번 묻지 않고 학습 — 질문이 0으로 수렴
deny-bounded
위험 명령은 사람·ORCH도 우회 불가한 한계선에서 자동 거부

task 라이프사이클

각 task는 분해 → 작업 → 리뷰 → 완료의 공정을 거칩니다. 리뷰에서 합의 차단이 나오면 사람 없이 작업 단계로 되돌아가 자동 수정됩니다.

작동 원리 합의

합의 게이트

task가 끝날 때마다 투표 리뷰어 3종이 각자 독립 컨텍스트에서 차단 투표를 합니다. 한 명의 단독 거부권이 아니라 합의입니다.
만장일치 차단이면 사람 없이 수정시키고, 의견이 갈리면 사람을 부릅니다.

alignment
plan 정합
결과물이 plan의 의도·기준에서 벗어나지 않았는지 검토.
quality
코드 품질
구현의 견고함·테스트의 실효성을 검토.
security
보안
취약점·권한 누수·계약 위반을 검토.
합의 게이트 — T3 멱등성 실차단 예시
# 워커: 테스트 64개 전부 통과 — "끝났다"
 
alignment-rev blocking spec 계약 위반 — 테스트가 구현에 맞춰 작성됨
quality-rev blocking JWT 키 불일치 — 실 인증에선 전 요청 500
security-rev blocking IDOR — 타 사용자 자원 접근 가능
 
⟳ 만장일치 차단 → 자동 수정 지시 (사람 개입 0)
🎯
게이트가 잡은 false green: 테스트 64개가 전부 통과했지만
① JWT 키 불일치로 실 인증에선 전 요청 500 ② 테스트가 구현에 맞춰 작성돼 spec 계약 위반.
둘 다 자기보고로는 못 잡습니다.

STEP 5 리스트 관리

허용 · 차단 리스트

게이트의 판정 기준은 두 개의 리스트입니다 — 고정된 deny와 자라나는 allow. 어디에 있고 어떻게 관리하는지 정리합니다.

deny — 기본 차단 21종 (하드코딩, 작업 중 변경 불가)

harness/bin/danger-check.sh 읽기 전용
rm -rf · sudo · git push --force · git reset --hard · git clean -f
curl|sh · wget|sh · eval stdin · fork bomb · dd 쓰기 · chmod 777
~/.ssh · 자격증명 파일(.env 등) · 시스템 설정 쓰기 · $HOME/하니스 삭제 …

allow — 기본 허용 10 카테고리 + 학습

역할별로 자동 허용되는 카테고리입니다. 카탈로그는 📄 harness/config/orch-auto-allow.yaml에 있고, 작업 중 승인한 패턴은 런타임 📄 .agent-harness/learned-allow.yaml에 누적됩니다(재가동에도 유지).

read-only version-probe git-readonly safe-test safe-build dev-deps safe-fs git-write self-verify harness-infra learned ← 승인 패턴 누적

리스트를 보고 관리하기

허용 카탈로그는 git 추적되는 원본 파일이므로 직접 열어 확인·수정할 수 있습니다. 차단 리스트는 안전을 위해 코드에 하드코딩돼 있어 작업 중 변경되지 않습니다.

terminal — bash
# 허용 카탈로그 보기 (역할별 자동 허용 규칙)
$ cat harness/config/orch-auto-allow.yaml
 
# 작업 중 학습된 허용 패턴 보기 (런타임, 재가동에도 유지)
$ cat .agent-harness/learned-allow.yaml
🔒
차단 21종은 작업 중 우회·해제할 수 없습니다. 사람도 ORCH도 못 끕니다 — 이것이 deny-bounded의 핵심입니다.
허용 카탈로그를 넓히고 싶으면 git 추적되는 원본 yaml을 직접 수정하세요(런타임 파일이 아니라 원본에서).
STEP 1 멀티프로젝트

멀티프로젝트 동시 진행

AWA는 한 번에 한 프로젝트만 다루지 않습니다. 서로 다른 폴더에서 팀을 각각 띄우면, 세션 이름이 폴더 이름으로 자동 분리(awa-<폴더명>)되어 독립된 팀으로 동시에 굴러갑니다.
한 프로젝트의 작업이 다른 프로젝트에 새지 않습니다.

terminal — bash
# 프로젝트 A 팀 — 세션 awa-projA 로 자동 격리
$ awa-up.sh --spec /path/projA/.awa/team.yaml --project /path/projA
 
# 프로젝트 B 팀 — 세션 awa-projB, A 와 완전 독립
$ awa-up.sh --spec /path/projB/.awa/team.yaml --project /path/projB
 
✓ awa-projA · ✓ awa-projB — 두 팀 동시 가동
🧩
실무에선 /awa 인터뷰가 이 과정을 대신합니다. 프로젝트마다 /awa를 실행해 폴더를 고르면 위 명령을 알아서 만들어 줍니다.
폴더 이름이 같아 충돌하면(awa-app 둘) SESSION_OVERRIDE="awa-app2"를 앞에 붙여 이름을 구분합니다.
🛰️
여러 팀이 동시에 돌면 화면을 오가기 번거롭습니다. 그래서 여러 프로젝트를 한 화면에 모으는 관제탑이 있습니다.
STEP 2 멀티뷰

멀티뷰 관제탑

여러 프로젝트의 ORCH·DESK 화면만 뽑아 한 윈도우 그리드(_DASHBOARD)에 모아 동시에 감시합니다. 첫 화면에서 본 그 대시보드입니다.
프로젝트마다 한 줄(왼쪽 ORCH, 오른쪽 DESK), 한 윈도우에 3개까지, 그 이상은 다음 페이지로 넘어갑니다.

_DASHBOARD — 2 projects 멀티뷰
projAORCH분해·배정·종합DESK사용자 창구
projBORCH리뷰 종합 중DESK대기
 
# 한 화면에서 두 프로젝트를 동시에 감시

관제탑 명령

/awa dash merge <A> <B>
여러 세션을 새 관제탑으로 모음
/awa dash add <C>
이미 떠 있는 관제탑에 한 프로젝트 추가
/awa dash detach <proj>
한 프로젝트를 관제탑에서 떼어 원래 세션으로 복원
/awa dash split
전부 복원하고 관제탑을 닫음
/awa dash kill <proj>
관제탑에서 떼고 그 프로젝트 팀까지 종료
📺
인터뷰에서 멀티뷰 모드를 고르면(이미 떠 있는 팀이 있을 때만 물어봅니다) 새 팀이 자동으로 관제탑에 합류합니다.
진입은 tmux attach -t _DASHBOARD
STEP 3 재개

재개 · 재접속

세션은 일회용이지만 흐름은 컨텍스트가 아니라 파일에 저장됩니다. 그래서 두 가지로 "이어서" 할 수 있습니다.
살아있는 팀에 다시 접속하거나, 정리했던 팀을 다시 띄우거나.

살아있는 팀에 재접속 (Step 0)

/awa를 실행하면 가장 먼저 지금 떠 있는 팀 목록을 보여줍니다. 하나를 고르면 새로 띄우지 않고 바로 tmux attach로 들어갑니다.
잠깐 자리를 비웠다 돌아올 때의 경로입니다.

이전 구성으로 다시 띄우기

떠 있는 팀이 없으면, 같은 폴더의 📄 .awa/team.yaml이 남아 있을 때 이전 팀 구성을 그대로 재사용할지 물어봅니다. 인터뷰를 다시 거치지 않습니다.

중단 지점부터 이어서

다시 띄우면 ORCH가 완료 증거(results/)를 대조해 완료한 작업은 건너뛰고 중단 지점부터 재개합니다. 같은 작업을 다시 하지 않습니다.

🔁
우선순위: 살아있는 세션 접속 > 이전 team.yaml 재사용 > 새 인터뷰. 세션 상태를 따로 저장/복원하지 않으므로, 가이드·프롬프트 수정은 항상 git 추적되는 원본 파일에서 하세요. 세션은 prompts/ + .awa/team.yaml로부터 매번 재생성됩니다.
STEP 4 북마크

프로젝트 북마크

여러 프로젝트를 오가다 보면 매번 긴 경로를 입력하기 번거롭습니다. AWA는 팀을 띄울 때마다 그 프로젝트 경로를 북마크에 자동으로 기록하고, 별칭을 붙이면 /awa 폴더 선택에서 경로 대신 별칭만 입력하면 됩니다.

/awa bookmarks list
저장된 프로젝트 전체 보기 (없어진 경로는 stale 표시)
/awa bookmarks set-alias
프로젝트에 짧은 별칭 부여·변경
/awa bookmarks remove
번호로 삭제 (1,3 또는 all)
/awa bookmarks prune
없어진 경로(stale) 일괄 정리
💾
북마크는 📄 ~/.config/awa/bookmarks.tsv에 저장됩니다.
프로젝트 폴더가 아니라 사용자 홈 설정이라 AWA를 다시 설치해도 북마크와 학습된 권한은 보존됩니다.
STEP 5 마무리

드레인 · 정리

작업을 중간에 끊지 않고 깔끔하게 멈추는 흐름입니다. 진행 중인 것만 마무리하게 두고(드레인), 세션을 정리하면(산출물은 보존) 다음에 이어서 띄울 수 있습니다.

드레인 — 진행 중인 것만 마치고 정지

DESK 화면에 "오늘은 여기까지"·"일시정지"처럼 자연어로 말하면, ORCH가 신규 배정만 중단합니다.
이미 진행 중인 task는 리뷰·종합까지 정상 처리하고 중단 지점을 기록합니다.

정리 — 산출물 보존

/awa down 메뉴로 정리할 세션을 고르면 tmux 세션과 런타임 파일을 정리합니다. 코드·결과물 같은 산출물은 그대로 남습니다.

terminal
> 오늘은 여기까지# DESK 에 — 드레인(진행분만 마치고 정지)
> /awa down# 정리 메뉴 (산출물 보존)
> /awa# 다음 날 — 중단 지점부터 재개
♻️
멈췄다 이어도 손실이 없는 건 흐름이 파일(tasks/·results/)에 있기 때문입니다. 그래서 "오늘 여기까지 → 정리 → 내일 재개"가 자연스러운 일상 루틴이 됩니다.
